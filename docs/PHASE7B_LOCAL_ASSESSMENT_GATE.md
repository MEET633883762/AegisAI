# Phase 7B — Local assessment gate

> Current setup: use Python 3.11 from the [development guide](DEVELOPMENT.md). PowerShell examples run from the repository root with `.\.venv\Scripts\python.exe`; on Linux use `.venv/bin/python`. Phase-specific verification counts are historical; see [current status](CURRENT_STATUS.md) for fresh checks.

This increment establishes a standalone, bounded policy/controller and operator-invoked runner for harmless HTTP observations against the synthetic test site at `http://127.0.0.1:8767`. It supports only versioned checks `health_status_v1`, `security_headers_v1`, and `cookie_attributes_v1`. Requests are fixed `GET`s to `/health` or `/`; the runner accepts only an optional local `--database` output path and callers cannot supply target paths, methods, request bodies, check catalogs, or target overrides. The policy checks the exact loopback origin and port immediately before each request.

The gate is intentionally separate from `controller.Controller` and `ControllerPolicy`. The existing Controller authorizes Red/Blue simulator actions and then invokes the simulator; it has no HTTP-check action type. Reusing it for a website request would execute an unrelated simulator action. The local assessment policy makes its own allow/deny decision and the assessment controller sends a request only after an allow decision.

Requests have a one-second timeout, a four-second assessment deadline, a three-request maximum, and separate 16 KiB caps for response bodies and headers. Redirects are disabled; the `Location` target is classified against the exact approved origin and allowlisted paths, and no redirect is followed. Results include check IDs, allow/deny decisions, response status, observed properties, elapsed time, evidence metadata, and sanitized error categories. The body is represented by a bounded byte count and digest, not retained in the result. Header absence or cookie attributes are observations only; this increment does not assert a confirmed vulnerability. Cookie checks report not applicable when no cookie is returned and never return the cookie value. Reasons returned for denied or failed checks are fixed codes and do not contain request data or exception text.

Run the site in one terminal with `.\.venv\Scripts\python.exe -m demo_site.telemetry_server`, then run the fixed assessment in another with `.\.venv\Scripts\python.exe scripts/run_local_assessment.py`. The dedicated site writes synthetic access/error logs under the ignored `.aegisai-local/website-telemetry/` directory. The runner stores the sanitized report under the fixed local synthetic tenant in the private API SQLite store. Schema version 4 adds tenant-scoped assessment report, observation, and report-to-observation tables. Observation identities are deterministic from observed properties and response digest, excluding capture time and duration; repeated observations are stored once. Reports retain the latest 20 per tenant. Each store operation records a categorical `protected_operation` audit event in the same transaction. No body text, cookie values, credentials, or raw log lines are persisted.

Focused verification: `.\.venv\Scripts\python.exe -m pytest -q tests/unit/test_local_assessment.py`.

Current integration: persisted reports are now exposed through authenticated `GET /api/assessment/reports/latest` with the `reports:read` scope and the local dashboard's Assessment view. The API derives tenant scope from the bearer principal. The dashboard can inspect the latest report and retained comparisons but cannot authorize or launch checks. See [the validation engine](PHASE2_SECURITY_VALIDATION_ENGINE.md) for catalog and reporting details. Assessment observations are still not automatically correlated with the site's generated access/error log records.
